# ADR 0011 — SSE para atualização em tempo real

- **Status:** Aceito
- **Data:** 2026-02-11
- **Contexto relacionado:** Escopo _Should_ de tempo real na triagem (milestone M2) <!-- preencher com a issue quando ela for criada -->

## Contexto

Vários analistas trabalham na mesma fila. Quando um colega assume ou fecha um caso, os outros deveriam saber — sem isso, dois analistas ligam para o mesmo motorista, que é uma das dores centrais da persona. Há, porém, uma restrição de experiência que se sobrepõe à de sincronização: **a lista não pode reordenar sozinha sob o cursor da analista**, porque reordenar durante a varredura faz a linha mudar de lugar entre a decisão e o clique. A comunicação necessária é unidirecional e de baixo volume: servidor → cliente, com eventos pequenos.

## Decisão

**Server-Sent Events** em `GET /api/v1/incidents/stream`, com eventos nomeados por tipo:

```
event: incident.created
data: {"id":"…","code":"INC-2026-000124","criticality":"ALTA","priorityScore":1210}

event: incident.updated
data: {"id":"…","version":5,"status":"FECHADO"}

: heartbeat
```

O cliente consome os eventos para **incrementar um contador** — _"3 novos incidentes"_ — e nunca para mutar a lista diretamente. A atualização acontece sob ação explícita, e nesse momento um `refetch` fecha a lacuna de eventos perdidos. O servidor envia um comentário de _heartbeat_ periódico, que mantém buffers de proxy fluindo e detecta conexões mortas.

## Alternativas consideradas

- **WebSocket.** Descartado: protocolo bidirecional para um fluxo que só precisa receber. Traria _handshake_, _ping/pong_, reconexão manual e — o ponto decisivo — um _upgrade_ de protocolo que proxies corporativos e CDNs frequentemente bloqueiam. SSE é HTTP comum, atravessa o caminho existente e reconecta sozinho no `EventSource`.
- **Long polling.** Descartado: cada ciclo reabre requisição e reenvia cabeçalhos; o atraso fica limitado pelo intervalo, e o custo por cliente conectado é maior.
- **`refetchInterval` no TanStack Query (polling).** Considerado seriamente por ser a solução mais simples, e descartado porque **reordena a lista a cada ciclo** — exatamente o comportamento proibido — e não distingue "chegou um incidente novo" de "a lista continua igual", o que impede alimentar o contador.
- **Publicar eventos em Redis e consumir por SSE.** Descartado: adiciona infraestrutura para um requisito que, com uma única instância de API, não existe. É o ponto mais provável de revisão deste ADR se o deploy passar a ter múltiplas réplicas.

## Consequências

### Positivas

- Atravessa proxy e CDN por ser HTTP comum, sem configuração de rede especial.
- `EventSource` **reconecta automaticamente**, com `Last-Event-ID`, sem código de reconexão no cliente.
- Mais simples de implementar e depurar que WebSocket: dá para ver o stream no `curl` e inspecionar no DevTools.
- Preserva a decisão de UX central: a lista nunca reordena sem ação explícita.

### Negativas / trade-offs

- **Unidirecional.** Um caso de uso futuro de cliente → servidor em tempo real exigiria outro mecanismo ou migração para WebSocket.
- **Limite de conexões por domínio no HTTP/1.1.** Com SSE e requisições comuns no mesmo domínio, o navegador limita a concorrência; em HTTP/2 ou HTTP/3, que é o que o deploy serve, o limite não se aplica.
- **Buffer de proxy**: se o caminho não repassar a resposta incrementalmente, os eventos chegam acumulados. Mitigado pelo _heartbeat_, mas é a causa mais comum de "funciona local e não em produção".
- **Uma conexão aberta por analista.** Com `async def` o custo é baixo, mas não é nulo: um número muito alto de conectados exigiria _fan-out_ por Redis.
